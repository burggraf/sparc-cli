Supabase CLI tag [`v2.117.0`](https://github.com/supabase/cli/tree/v2.117.0), commit `21db855916f2` (the locally installed CLI reports `2.117.0`). No hosted writes were made for this review. ## What the CLI actually emits

The [command](https://github.com/supabase/cli/blob/v2.117.0/apps/cli/src/commands/db/dump/dump.command.ts) and [handler](https://github.com/supabase/cli/blob/v2.117.0/apps/cli/src/commands/db/dump/dump.handler.ts) choose one of three *plain SQL* modes: schema by default, `--data-only`, or `--role-only`. The handler defaults data to column INSERTs; `--use-copy --data-only` selects COPY. `--exclude/-x` applies to data-only dumps. Modes are separate, not one full-database dump. The Go [options/exclusion lists](https://github.com/supabase/cli/blob/v2.117.0/apps/cli-go/pkg/migration/dump.go) are also ported into the TS [environment builder](https://github.com/supabase/cli/blob/v2.117.0/apps/cli/src/command-internal/legacy-pg-dump.env.ts).

| Mode | v2.117.0 behavior | Consequence for SPARC |
| --- | --- | --- |
| Default schema | [`pg_dump --schema-only --role postgres`](https://github.com/supabase/cli/blob/v2.117.0/apps/cli-go/pkg/migration/scripts/dump_schema.sh), with `InternalSchemas` excluded by default: `auth`, `storage`, `supabase_migrations`, other platform and extension schemas. SQL is postprocessed with many `sed` rewrites, e.g. `CREATE SCHEMA IF NOT EXISTS`, publication/event-trigger suppression, some owner/grant suppression. | Preserve application DDL (including `public` objects and ACL/RLS) but do not replay managed baselines. A schema exclusion does **not** prove that every database-wide extension/publication/ACL command is safe; classify these separately. Do not copy text rewrites blindly. |
| Data | [`pg_dump --data-only`](https://github.com/supabase/cli/blob/v2.117.0/apps/cli-go/pkg/migration/scripts/dump_data.sh) with a *different* `excludedSchemas` list. `auth`, `storage`, `supabase_functions`, `cron`, `net`, `pgmq`, and `dbdev` are **not excluded by that list**. Three tables are always excluded: `auth.schema_migrations`, `storage.migrations`, `supabase_functions.migrations`. Script emits `SET session_replication_role = replica` before data and `RESET ALL` afterward. | Include only qualified application/Auth/Storage table data; explicitly gate other service/extension tables, which upstream's broad selection could otherwise include. The script's setting requires the data to run in the **same target session**; test actual permission, and verify the effects of disabled normal triggers/FK enforcement. |
| Roles | [`pg_dumpall --roles-only --no-role-passwords --no-comments`](https://github.com/supabase/cli/blob/v2.117.0/apps/cli-go/pkg/migration/scripts/dump_role.sh), then text-filters reserved role create/alter statements, unsafe attributes, some membership grants and role settings. | Global roles are **not** in SPARC's single-database `pg_dump`. Inventory custom roles/ownership/memberships independently; don't paste SQL with incomplete grant/owner filtering. LOGIN passwords are not captured and require deliberate replacement. |

**Override hazard:** [`DumpSchema`](https://github.com/supabase/cli/blob/v2.117.0/apps/cli-go/pkg/migration/dump.go) supplies `--schema=…` **instead of** the default `EXCLUDED_SCHEMAS` when a schema is explicit. [`DumpData`](https://github.com/supabase/cli/blob/v2.117.0/apps/cli-go/pkg/migration/dump.go) likewise replaces its default inclusion/exclusion set when `--schema` is explicit, though its three fixed `--exclude-table` flags remain. `--schema auth` is **not** a safe way to select only custom Auth DDL. The guide intentionally uses explicit `supabase_migrations` only for a separately handled migration-history transfer.

The [official guide](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore) prescribes three dumps (`--role-only`, default schema, `--data-only --use-copy`), additionally excludes `storage.buckets_vectors` and `storage.vector_indexes` in its data example, and restores with `psql --single-transaction --variable ON_ERROR_STOP=1` and `SET session_replication_role = replica`. It explicitly treats custom `auth`/`storage` triggers/policies, CLI migration history, managed-role permission errors, Vault/column-encryption root keys, Realtime publication reactivation, and Storage object *file bytes* as separate work. Its recommended connection string / plaintext output-file workflow is **not** SPARC's credential/encryption design.

## SPARC selection contract (proposed; not yet executable)

| Category | Default selection for the database-only recipe | Refusal, omission, or additional requirement |
| --- | --- | --- |
| Application schema DDL | Objects owned by qualified application schemas (including ordinary `public` objects): tables, sequences, types, routines, triggers, policies, indexes, constraints, and security metadata; inspect and preserve owners, ACLs, defaults, RLS. | Treat the pre-existing `public` schema itself and all database-scoped commands separately. Extension objects, publications, large objects, foreign/external objects, event triggers, unknown TOC types and schema collisions need explicit handling; no broad `--clean`, `--no-owner`, or `--no-acl` to paper over differences. |
| Managed schema DDL | **Exclude baseline DDL** for `auth`, `storage`, `supabase_functions`, `supabase_migrations`, and the remaining upstream internal/extension schema list. | Detect application-added managed-schema objects or policies/triggers from authoritative migrations or a reviewed baseline diff. Preserve them by an explicit reviewed migration path; if detection cannot distinguish customizations from provider version drift, classify **unknown and block** a completeness claim. |
| Qualified table data | Application tables plus compatible `auth` records and ordinary `storage` metadata, including table rows and sequence values, only after checking destination columns/identity, dependencies and target permissions. | Exclude the three platform migration tables above; also exclude vector Storage tables from the default attempt. A table unknown to the selection profile, or one owned by a service/extension, is a refusal/unknown rather than silently copied. Storage database rows are **not** object bytes or an accessible Storage service. |
| Other service/extension data | **None automatically**, even when CLI v2.117.0's `excludedSchemas` does not name `cron`, `net`, `pgmq`, `dbdev` or `supabase_functions`. | Detect and report `cron` jobs, `net` requests, queues, functions and specialty objects; decide whether state is durable, transient, side-effectful or needs manual/isolated migration. `cron`/`net` already differed between the trial target and live source. Extension versions on the fresh target must be qualified. |
| Migration history | No replay of migration SQL; default platform migration-history table rows excluded. | Supabase CLI history in `supabase_migrations` is separately opt-in per the guide. Preserve version metadata as inert records with a reviewed target-baseline collision policy; until then mark migration history incomplete, not silently lost or equated to schema DDL. |
| Roles and grants | Only reviewed **custom** roles, required membership edges, and object grants, in dependency order; never reset provider-managed accounts automatically. | Upstream `reservedRoles` includes `cli_login_.*`, `postgres`, `supabase_.*`, `anon`, `authenticated`, `service_role` and others. The source-only `cli_login_postgres` matches Supabase CLI's reserved login-role pattern and is **not** a missing application role to replay. Review grantor/admin option and owner compatibility; manual passwords for custom LOGIN roles. Until custom-role capture exists, report the role gap as incomplete. |
| Unknowns | Enumerate every excluded, absent, unsupported and unknown class in the encrypted recovery profile and public non-secret report. | Refuse a complete/verified restore claim for an unclassified applicable object. Detection/refusal does not transform it into restored coverage. |

**Trigger caveat:** `session_replication_role = replica` suppresses ordinary triggers, including FK enforcement, and can change application side effects; triggers configured `ALWAYS`/`REPLICA` may still fire. In a read-only transaction on the earlier disposable target, `SET LOCAL` succeeded and a readback showed `replica` despite `has_parameter_privilege` returning false. That observation is **not** a restore test or permission guarantee for a future project. Use a tested, scoped same-session data transaction and integrity/behavior checks; fail closed if unsupported.

**Snapshot caveat:** separate schema/data/role dumps need an explicit consistency strategy (quiet source or a qualified shared PostgreSQL snapshot for compatible database passes). A sequence of successful dumps alone is not one archive-time snapshot; cluster roles and non-database services are outside the database snapshot.

## Archive compatibility decision for Tasks 2 and 4

Choose **an encrypted, versioned `database/recovery-profile.json` component inside existing `sparc-archive` version 1**, not a container-format version 2. Existing v1 supports multiple encrypted components and validates their unique keys; a new optional top-level manifest field would be rejected by the strict parser. Version the recovery profile's own JSON schema and bind it to exactly specified component keys/scopes, ordered dump modes, tool/PG versions, exclusions, unknowns and their dispositions. Validate its complete shape *after authenticated archive verification and before target access*; refuse unknown profile versions/keys/statuses. The profile records scope, not a proven source snapshot or a completed restore.

- **Legacy:** exactly one `database/postgresql.dump` component with its existing scope/status remains the old full custom-format dump, always `incomplete`. `./tmp/test` stays byte-for-byte as is. Derive an offline selection from its authenticated TOC and explicitly report uncaptured roles/non-database state; do not fabricate a new profile, reinterpret the dump as split, or promise every managed customization can be recovered.
- **New capture (planned):** distinct encrypted schema/data payloads plus `database/recovery-profile.json`; custom-role payload only after a qualified capture path exists. Selectors must recognize the new profile key and require the exact allowed payload set; legacy validation remains a separate branch. `internal/database/capture.go` currently requires exactly the one legacy key, so this is **not implemented** by the archive-format choice alone. Keep overall coverage `incomplete` while any required component is missing.

Why not version 2 now? Container v1 already handles multiple encrypted payloads; a new version would change parsing/verification for no demonstrated benefit. Switch only if future semantics need different cryptography, integrity, or container layout. Never make an unknown/new profile fall back to legacy behavior.

## Task 2 offline-selector evidence (2026-09-28)

The developer-only selector parses bounded `pg_restore --list` metadata into separate numeric schema/data TOC-ID arrays, preserving order within each phase. It reports counts only. It excludes the known Auth/Storage migration tables and the two Storage vector tables, permits application/Auth/Storage data, and blocks on managed Auth/Storage DDL, other protected schemas, unsupported classes or unknown TOC descriptions. Ambiguous whitespace in schema names is refused. Unit fixtures cover quoted/spaced relation names, parent/child FK ordering, ownerless extension entries, migration/vector rows, service data and unknown descriptors. A synthetic custom-format PostgreSQL 17.9 archive was generated and inspected on a private disposable local cluster; the native TOC parser selected application schema/data entries without static blockers. This also fixed valid ownerless `EXTENSION` records and quotes inside ACL/signature tokens. A zero-entry per-schema filter is accepted as count 0.

The owner supplied `.env.passphrase` locally; offline `sparc verify` reported integrity passed with capture declaration `incomplete`. `sparc-localrestore --inspect` classified the authenticated `./tmp/test` TOC (1,081 total): 454 proposed application-schema entries, 57 proposed eligible data entries, 4 excluded migration/Storage-vector data entries, 365 managed-schema DDL entries requiring review, 200 unsupported entries, and 1 unknown entry. The separate extension count was 6 (a subset of unsupported entries). Static selection is blocked; no names, SQL, or passphrase were printed. These counts are not restore/fidelity evidence. No hosted connection/write occurred.

The selector is not restore approval; source/target role compatibility, managed-schema diffs, cross-database dependencies, destination state, archive-time row equivalence, and Auth/Storage service behavior remain unverified.
